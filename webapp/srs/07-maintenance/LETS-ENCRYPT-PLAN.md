# Let's Encrypt plan — replace the locally generated TLS pair with ACME

Scope: the HTTPS the webapp serves today (`webapp/hix.json` → `server.ssl = true`) stops being a
self-signed certificate generated by `./gen_cert.sh` and becomes a **Let's Encrypt** (ACME)
certificate obtained with `certbot`, wired into the same two config keys the framework already
documents (`cert_private` ← `privkey.pem`, `cert_public` ← `fullchain.pem`).

Status: **plan only.** No phase below has been executed. `certbot` is **not installed on this
machine** (`which certbot` → not found, rc 127), no reverse proxy is installed (`which nginx
apache2 caddy` → all empty), and there is **no deployed instance of this app anywhere in this
repository** — the only workflow is `.github/workflows/docs.yml` (MkDocs deploy). P1 below is
therefore a blocking decision, not a formality.

Date: 2026-10-07. Flag names below were taken from the Certbot 5.8 documentation
(<https://eff-certbot.readthedocs.io/en/stable/using.html>) on that date. Certbot's flags have
changed across versions (`--webroot-path` vs `-w`, the renewal threshold moved from a fixed 30 days
to 1/3 of lifetime in Certbot 4.0.0); **re-check with `certbot --help certonly` and `certbot
certificates` on the target box before running anything here.**

## 1. Ground rules (binding — read before running anything)

| Rule | Why |
|---|---|
| `gen_cert.sh` stays; it is **not** deleted, only demoted to the dev path | It is the launcher's idempotent bootstrap (`webapp/go_gcc.sh:120-121`) and the only thing that keeps a fresh clone startable. Removing it breaks every local build. |
| No key, no `.pem`, no ACME state is ever committed | `webapp/.gitignore:21` already ignores `certs/`; the framework's own rule is `site-docs/en/hixstyle/seguridad/ssl.md` §Best practices 6, "No committed keys". A Let's Encrypt **private key** is the same class of secret as `hix.key`. |
| Run `--dry-run` (staging server) before the real issuance call, every time | `--dry-run` "performs a test run against the Let's Encrypt staging server" (Certbot docs). Real issuance is rate-limited per domain (duplicate-certificate and too-many-requests limits); a typo that costs a real issuance also costs a lockout. |
| Never point `certbot` at a domain we do not own | ACME issuance is an outbound, third-party, **irreversible-within-the-day** action. This is a stronger constraint than the local-only rule in `webapp/srs/VIGOLIUM-SCAN-PLAN.md` §1: that plan forbids outbound requests entirely; this one cannot, so the domain must be explicitly ours. |
| Do not run `certbot --nginx` / `certbot --apache` | Those plugins rewrite a third-party server's config. Neither exists here, and the DEV-compliance rule forbids changes outside the project folder. Use `certonly` + explicit wiring. |
| `--standalone` binds port 80 and **stops nothing else** — but it must be free | Certbot docs, Standalone: "This plugin needs to bind to port 80… you may need to stop your existing webserver." The app listens on 9090 (`webapp/hix.json:9`), so it does not collide; anything else on the box that owns 80 does. |
| Renewal **must** restart `./app` | The SSL context is built once per process (evidence §3, L-01). A renewed certificate without a restart is not served. This is the plan's most error-prone element; it is not optional. |
| HSTS is already being sent, unconditionally, forever | `src/mw/hix_mw_secheaders.prg:91` emits `Strict-Transport-Security: max-age=31536000` on every response. Once the real domain is served, a browser pins it for a year. Any later HTTP fallback, port change, or domain change is unrecoverable in that browser. See R-1. |
| Record evidence, do not claim results | Same discipline as `PENTEST-REPORT.md`: every claim in a later report needs the command, the output, and the `file:line` that explains it. |

## 4. Decision points (record the answer; the phases below assume these)

**D-1 — where TLS terminates.** Two shapes, and they are not interchangeable.

| | (a) HIX terminates TLS directly | (b) reverse proxy terminates TLS |
|---|---|---|
| `server.ssl` | `true` | `false` |
| `server.mode` | `standalone` | `proxied` (`src/hix_request.prg:54` reads `X-Forwarded-*`) |
| Certificate lives | in `paths.certs`, read by `./app` | in the proxy (`SSLCertificateFile`/`KeyFile`, ssl.md §Behind a proxy) |
| Renewal restart | **must restart `./app`** (L-01) | restarts the proxy only |
| Privileged port | 443 for the app + 80 for the ACME challenge | 443/80 for the proxy |
| Framework's own advice | ssl.md §Best practices 4: "Behind a proxy in prod… HIX stays on the internal network serving plain HTTP" | |

**Pick (a) for this plan** — it is the literal replacement asked for (the webapp's own TLS
changes source), it keeps `hix.json`'s shape, and it needs no third-party server, which the
"no 3rd Party WEB UI / only HIX + Harbour" constraint in `webapp/srs/DEV-compliance.md` leans
against. Record (b) as the alternative and its consequence: under (b) the ACME pair never touches
`webapp/certs/`, `server.ssl` becomes `false`, and `trusted_proxies` (`webapp/hix.json:14`) plus
`X-Forwarded-Proto` become load-bearing for `UIsHttps()` and for the CSRF/session `Secure`
decision. Do not do (a) and (b) at once: two TLS terminations on one domain is a silent
misconfiguration.

**D-2 — challenge type.** HTTP-01 via `--standalone` (default choice: binds 80, needs the domain
publicly resolvable, needs 80 free). `--webroot` writing into `webapp/www/` is **not** assumed to
work: HIX's docroot is routed (`dispatch_mode: full`, `webapp/hix.json:38`), and whether
`GET /.well-known/acme-challenge/<token>` is served as a static file or 404'd by the dispatcher is
unverified — probe it (P3-alt) before relying on it. DNS-01 / wildcard is out of scope here (no
DNS plugin installed, and a wildcard would widen the certificate to `*.domain`, which the app's
router does not currently model).

**D-3 — where the PEM pair sits for the app.** Options, with the failure each avoids:

| Option | How | Verdict |
|---|---|---|
| (i) symlinks in `certs/` | `certs/hix.key → /etc/letsencrypt/live/<name>/privkey.pem`, `certs/hix.crt → …/fullchain.pem` | **Chosen.** Renewal repoints the `live/` symlinks atomically, so the app's config never changes; `webapp/.gitignore:21` already hides `certs/`. Requires the app user to be able to read the root-owned `archive/` files → see D-4. |
| (ii) copy the pair into `certs/` | `cp` on every issuance **and** every renewal | Rejected as the default: a copy drifts silently after the next renewal and re-creates L-02's "starts, then fails every request" failure mode. Acceptable only if the copy is inside certbot's `--deploy-hook`. |
| (iii) `paths.certs` = absolute live dir | `hix.json:32` → `/etc/letsencrypt/live/<name>` | Works (`hb_DirSepAdd` + name yields a valid absolute path, `src/hix_io.prg:31-46`), but it puts a domain-specific absolute path into the committed config and makes a fresh clone unstartable. Keep `certs/` relative. |

**D-4 — who may read the private key.** `/etc/letsencrypt/live/<name>/privkey.pem` is a symlink into
`archive/`, which certbot keeps root-owned `0600`. The app runs as an unprivileged user, so it
cannot read it, so `SSL_CTX_USE_PRIVATEKEY_FILE` returns ≠ 1 at `src/hix_io.prg:553` and the server
starts and fails every request (L-02). Decide and record **one** of:

| | Mechanism | Notes |
|---|---|---|
| (α) ACL | `setfacl -R -m u:<appuser>:rX /etc/letsencrypt/live/<name>` (+ the parent dirs' `o+x`) | Chosen with (i). Explicit, survives renewal only if re-applied in the renew hook — `archive/<name>-NNNN/` is a **new directory each renewal**, so the ACL must be re-applied per renewal, not once. |
| (β) dedicated group | `chgrp` + `chmod g+s` on `live/` and each new `archive/` dir | Same re-application problem; needs certbot's umask to cooperate. |
| (γ) run `./app` as root | Rejected: the app serves a docroot, DBF data and a session store; running it setuid-root to read a key is not acceptable. |
| (δ) unprivileged certbot | `--config-dir <project>/.letsencrypt --work-dir … --logs-dir …` so the whole `live/`+`archive/` tree is user-owned | Also satisfies `webapp/srs/DEV-compliance.md` ("Adhoc tools… only in project folder. No change will be done outside project folder."). **Unverified**: confirm with `certbot certificates` after a `--dry-run` that the live/archive dirs really are under `--config-dir`, and that `--standalone` can still bind 80 (privileged port → `sudo`/`setcap` regardless). |

**D-5 — key type.** `gen_cert.sh` uses `rsa:2048` (`webapp/gen_cert.sh:32`). Certbot's default is
`--rsa-key-size 2048`; `--key-type ecdsa` is the smaller/faster alternative. Keep RSA-2048 for
continuity unless the Harbour/OpenSSL build is confirmed to accept ECDSA P-256 in
`SSL_CTX_USE_PRIVATEKEY_FILE` — do not change both the CA and the key type in one step.

**D-6 — the dev path.** `gen_cert.sh` stays the default for any checkout without a recorded domain
(P6 gate). A fresh clone must remain startable.

### P1 — the domain decision (blocking)

Nothing in the repository names a host: `host: localhost` (`webapp/hix.json:8`), `allowed_hosts: ""`
(15), and no deploy target exists (only `.github/workflows/docs.yml`). ACME requires a
**publicly resolvable domain owned by us**; `localhost` can never validate. Record:

```
domain:            <fill in>
cert-name:         <fill in>            # certbot's own name; defaults to the first domain
email / SA:        <fill in>            # or --register-sa
TLS terminates:    (a) HIX direct       # D-1
key placement:     (i) symlinks         # D-3
key access:        (α) ACL              # D-4
```

Stop: no domain → the plan stops. Do not substitute a tunnel for a permanent domain: an ACME
certificate is bound to the name it validated.

### P2 — staging rehearsal (no real certificate)

```bash
sudo certbot certonly --standalone --dry-run \
     --cert-name <cert-name> -d <domain> \
     --rsa-key-size 2048 -n --agree-tos -m <email>
```

`--dry-run` uses the staging server and saves nothing (Certbot docs). Verify: the challenge
actually reached `<domain>:80` from Let's Encrypt's servers (a DNS record alone is not enough —
inbound connections on port 80 must be accepted, Standalone: "It must still be possible for your
machine to accept inbound connections from the Internet on the specified port").

Stop: any `NXDOMAIN`, `CURL_EASY_*`, or "Could not resolve" → fix DNS/reverse-proxy before issuing.

### P3 — issuance (the real one)

```bash
sudo certbot certonly --standalone \
     --cert-name <cert-name> -d <domain> \
     --rsa-key-size 2048 -n --agree-tos -m <email>
```

Then inventory what certbot produced:

```bash
certbot certificates
# expect: Certificate, Serial Number / Names: Domains: <domain>
#         Cert: /etc/letsencrypt/live/<cert-name>-NNNN/cert.pem
#         Private Key: …/privkey.pem   Chain: …/chain.pem   Full chain: …/fullchain.pem
```

Use `fullchain.pem` for `cert_public`, per the framework's own mapping (`ssl.md:77-78`):
`SSL_CTX_USE_CERTIFICATE_FILE` (`src/hix_io.prg:560`) reads the chain out of the same PEM, and
`cert.pem` alone leaves browsers unable to build the chain (`ERR_CERT_PATH_NOT_TRUSTED` class).

### P3-alt — the `--webroot` probe (only if D-2 is revisited)

Do not adopt without running the probe: place a token file under `webapp/www/.well-known/acme-challenge/`
and `curl -sk https://localhost:9090/.well-known/acme-challenge/<token>` through the running app.
If the dispatcher 404s it, `--webroot` is unusable against HIX and `--standalone` stays.

### P4 — wire the pair into `certs/` (the two names the app already expects)

```bash
umask 077
ln -s /etc/letsencrypt/live/<cert-name>-NNNN/privkey.pem  webapp/certs/hix.key
ln -s /etc/letsencrypt/live/<cert-name>-NNNN/fullchain.pem webapp/certs/hix.crt
```

`webapp/.gitignore:21` (`certs/`) already covers the symlinks themselves. Verify the app can
actually read them — this is L-02, and it is the failure the guard will **not** catch:

```bash
sudo -u <appuser> cat /etc/letsencrypt/live/<cert-name>-NNNN/privkey.pem >/dev/null; echo rc=$?
```

`rc != 0` → apply D-4 (α) before starting the app, and make the ACL part of the renew hook, since
each renewal creates a new `archive/<cert-name>-NNNN/` directory.

### P6 — the launcher and the guard (the only code-adjacent work in this plan)

Three things currently assert the dev path and will lie on a production install:

1. `webapp/go_gcc.sh:120-121` runs `./gen_cert.sh` unconditionally. With the LE symlinks in place
   its `openssl x509 -checkend 86400` guard (`gen_cert.sh:26`) follows the symlink and makes it a
   no-op — so it is *safe* today, but it is also *wrong in intent*. Gate it on a recorded domain
   (or on `app.env` + presence of `webapp/.letsencrypt`/`/etc/letsencrypt`) so a production
   install never regenerates a self-signed `localhost` pair over the ACME one.
2. `webapp/src/app.prg:376` prints "run ./gen_cert.sh first". On a production install that advice
   is false; the message should name the ACME path when `allowed_hosts` is set.
3. `_TlsGuard` (`webapp/src/app.prg:369`) checks existence, not readability (L-02). A pair that
   exists but cannot be read passes the guard, then fails at `src/hix_io.prg:553/560`, and the
   server starts and fails every request — the exact failure `_TlsGuard` exists to prevent.
   **This is the plan's real code change**: extend the guard to a readability test (open the file,
   not `File()`), so a permissions mistake is a startup refusal instead of a live-but-broken server.

All three are **plan entries**; nothing is edited by this document.

### P7 — renewal and restart (the load-bearing phase)

The SSL context is built once per process (L-01, `src/hix_server.prg:186/411/562`). Therefore
renewal is **renew + restart**, and the restart is not optional.

```bash
sudo certbot renew --deploy-hook '<restart ./app>'
```

`--deploy-hook` runs after a certificate is renewed (Certbot docs); `renew` "only renews
certificates that are near expiry, so it can be run as frequently as you want". The renewal
threshold is 1/3 of lifetime remaining as of Certbot 4.0.0 (docs), i.e. ~30 days on a 90-day
certificate — matching the framework doc's "Certificates expire after 90 days — certbot is
programmed to renew them automatically" (`ssl.md`).

Blocked on a process supervisor: `./app` is currently exec'd in the foreground by `go_gcc.sh`.
A `--deploy-hook` cannot restart a foreground process. Decide first: a systemd unit (outside the
project folder — DEV-compliance tension, see §6), a `certbot` cron + a project-local
`webapp/restart.sh`, or `--deploy-hook` into a supervisor that already exists. Record the choice;
do not leave the hook empty.

Verification after a renewal:

```bash
echo | openssl s_client -connect <domain>:443 -servername <domain> 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer
```

Expect `issuer=…ACME…`, `enddate` in the future, and the **new** `Serial Number` matching
`certbot certificates`. An unchanged serial after a renewal means the restart did not happen (L-01).

## 6. Compliance tension (must be stated, not silently resolved)

`webapp/srs/DEV-compliance.md` says: *"Adhoc tools, scripts, and alike should only be created in
project folder. No change will be done outside project folder."*

Let's Encrypt cannot obey that literally. Issuance is, by construction:

* an outbound HTTPS request to `https://acme-v02.api.letsencrypt.org/directory`,
* a public inbound connection on port 80 from Let's Encrypt's crawler,
* state in `/etc/letsencrypt/{live,archive,renewal}/` and `/var/{lib,log}/letsencrypt` (Certbot
  defaults: `--config-dir /etc/letsencrypt`, `--work-dir /var/lib/letsencrypt`,
  `--logs-dir /var/log/letsencrypt`),
* a package installation (`pacman -S certbot`).

Resolution to record: the compliance rule governs **the repository and this development box**
(Omarchy, no certbot, `localhost:9090`), and the ACME path belongs to a **separate production host**
where the rule is restated as "the repository still holds no key material" (`webapp/.gitignore:21`)
and "the only project-local artefacts are the two symlinks and, if D-4 (δ) is chosen, the
`--config-dir`". A `webapp/` script may *wrap* certbot; it may not *be* certbot. If D-4 (δ) is
chosen, re-read DEV-compliance with the production host as the scope and record that reading.

## 7. Risks and stop conditions

| # | Risk | Symptom | Stop condition |
|---|---|---|---|
| R-1 | HSTS is already permanent | `src/mw/hix_mw_secheaders.prg:91` sends `max-age=31536000` on every response, including today over `localhost` | Before the first public issuance, decide the final domain and whether `includeSubDomains` is wanted. After it, an HTTP fallback or a domain change is browser-unrecoverable for a year. Do not issue on a throwaway/tunnel name. |
| R-2 | Renewed cert not served | serial unchanged after `renew` (L-01) | Never run `renew` without the restart hook; treat an empty hook as a failure, not a success. |
| R-3 | Key unreadable, app "live but broken" | `SSL: invalid private key file` in the error log; every request fails (L-02) | P4's `sudo -u <appuser>` readability check before the first start; P6 item 3 makes it a startup refusal. |
| R-4 | Wrong PEM in `cert_public` | browser reports an incomplete chain | Use `fullchain.pem` (`ssl.md:77-78`); verify with `s_client` showing the full chain. |
| R-5 | Port 80 collision during issuance | `--standalone` fails to bind | Check `80` is free (and that nothing else on the box owns it) before P3. |
| R-6 | Real issuance burned by a typo | ACME rate limits / "too many requests" lockout | P2 `--dry-run` first, always; `--cert-name` set explicitly so a renewal cannot act on the wrong certificate (`certbot certificates` before any `renew`). |
| R-7 | Two TLS terminations | app on 443 with `ssl: true` **and** a proxy also terminating | D-1 is one choice only. |
| R-8 | Dev pair silently regenerated over the ACME pair | `gen_cert.sh` re-runs on a production install (P6 item 1) | Gate the launcher call; keep the `checkend` guard as a second line of defence. |
